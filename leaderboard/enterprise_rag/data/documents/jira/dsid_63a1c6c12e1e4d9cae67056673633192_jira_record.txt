Details & Summary:
Use a stepwise rollback that prioritizes correctness while keeping traffic flowing: (1) create a 90/10 traffic split sending 90% to the fallback model (redwood-open-7b-ptq) and 10% to the current INT8 path for ~20 minutes; (2) demote the INT8 quant profile on one instance group in the dedicated pool (ops-only) with `optimizer-toggle --tenant brightpost --group ig-1 --quant-profile staged`; (3) monitor p95/p99 latency and structured-output schema pass rate for ~15 minutes; (4) if stable, migrate traffic to PTQ in 10% increments every 10 minutes until reaching 100% on PTQ; (5) if a faster rollback is needed, run `optimizer-toggle --tenant brightpost --force-quant-off` to immediately revert quantization while preserving batch cache; (6) if latency persists even after removing INT8, reduce adaptive-batching by setting max-batch-size to 8 and `dynamic_queue=false` for the route.

- Start with a 90/10 traffic split sending 90% to the fallback model redwood-open-7b-ptq and 10% to the current INT8 path for about 20 minutes
- Demote the INT8 quant profile on one instance group in the dedicated pool using optimizer-toggle --tenant brightpost --group ig-1 --quant-profile staged
- After demoting, monitor p95 and p99 latency and the structured-output schema pass rate for about 15 minutes
- If metrics are stable, shift traffic to PTQ in 10% increments every 10 minutes until reaching 100% on PTQ
- If a faster rollback is needed, run optimizer-toggle --tenant brightpost --force-quant-off to immediately revert quantization while preserving batch cache
- If latency persists after removing INT8, reduce adaptive batching by setting max-batch-size to 8 and dynamic_queue=false for the route
