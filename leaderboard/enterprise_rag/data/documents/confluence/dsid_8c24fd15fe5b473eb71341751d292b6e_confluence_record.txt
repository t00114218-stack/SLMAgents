Enterprise Record: If Console shows a canary step change to a lower percentage 

Document ID: dsid_8c24fd15fe5b473eb71341751d292b6e
System Source: confluence
Details & Summary:
First confirm the control-plane target: fetch rollout from orchestrator (current step %) and compare to observed canary % per region over a 10-15m window. Then check the data plane in the affected region: (1) If router decision logs show configured_canary_percent still equals the old step (even though Console/orchestrator shows the lower %), it's stale config propagation (often watch disconnect / cache); verify per-region route config version/last-applied age and fix by forcing a router config resync/rolling restart in that region (or re-apply/reconcile), and pause/rollback if safety is at risk. (2) If configured_canary_percent matches the new lower % but the region's split stays biased, inspect router logs for cohort_key_source/cohort_key_present/fallback_source/hash_seed: missing stable key causing fallback (e.g., request_id/UUID gives correct aggregate % but no stickiness; legacy IP/route-only seed indicates wrong/old cohorting behavior). (3) If only one region shows legacy cohorting fields/behavior or different hash seed/fallback order, check router build/version by region; that's router version skew-mitigate by redeploying/rolling forward that region to the minimum router version, and optionally set canary_pct=0 for that region as immediate containment. Recommended mitigation when unsure: pause rollout; if any chance of overexposing canary, rollback to baseline; use kill switch only if normal pause/rollback cannot take effect. Longer-term: ensure routers have watchdog + periodic resync and recommend customers send X-Redwood-Cohort-Key or Idempotency-Key (and region affinity if needed) to make cohorting predictable.

- Confirm the control-plane target by fetching the rollout step percent from the orchestrator and comparing it to the observed canary percent per region over a 10 to 15 minute window.
- If router decision logs in the affected region show configured_canary_percent still equals the old step while Console or orchestrator shows the lower percent, the issue is stale config propagation in that region.
- To validate stale config propagation, check the per-region route config version and last-applied age in the affected region.
- Mitigate stale config propagation by forcing a router config resync or doing a rolling restart in that region (or re-apply and reconcile), and pause or rollback if safety is at risk.
- If configured_canary_percent matches the new lower percent but the region split remains biased, investigate cohorting key behavior rather than config propagation.
- Diagnose cohorting key issues by inspecting router logs for cohort key source and presence, fallback source, and hash seed, looking for missing stable keys causing fallback or legacy cohorting behavior.
- If only one region shows legacy cohorting fields or behavior or a different hash seed or fallback order, the likely cause is router version skew across regions.
- Mitigate router version skew by redeploying or rolling forward the affected region to the minimum router version, and optionally set canary percent to 0 in that region for immediate containment.
- When the cause is unclear, the recommended mitigation is to pause the rollout and rollback to baseline if there is any chance of overexposing canary.
- Use a kill switch only if normal pause or rollback cannot take effect.
- Longer term, ensure routers have watchdog plus periodic resync, and recommend clients send a stable cohort key header such as X-Redwood-Cohort-Key or Idempotency-Key to make cohorting predictable.

Additional Enterprise Context: Verified in production cluster telemetry and internal system documentation.
